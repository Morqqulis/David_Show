# AuroraAP (ap_invoice) — Project Reference

This document is the handoff for the next Claude session. Read it top to bottom before touching code. It records what is actually true about this codebase today (2026-07-29) and everything that has bitten us so far.

**Honest one-paragraph summary**: AuroraAP is a municipal Accounts Payable workflow demo for the City of Aurora. Eleven client feedback items were implemented in the last session, and the app is substantially more complete than it was: email intake with OCR, reassignment, server-side filtering and saved views on All Requests, a rich email template editor, a GL-to-department restriction model, and a coding-completeness gate that actually fires. It is still **not production-ready** for one overriding reason: **there is no auth layer** — every route is publicly accessible to anyone with the URL. Do not claim runtime verification you did not perform — see [§10](#10-verification-handoff-mandatory) and [§14](#14-things-previous-sessions-got-wrong-learn-from-these).

**A stale handoff file is worse than no handoff file.** This document was trusted while out of date once and that directly caused a shipped regression. If you change behaviour, change this file in the same session.

### Invoice lifecycle

1. **Create** — manual form ([/new](src/app/(site)/(app)/new/)), or **email intake**: a message reaches the monitored mailbox, Microsoft Graph posts a change notification to [/api/intake/graph](src/app/(site)/api/intake/graph/route.ts), and [intake-pipeline.ts](src/backend/lib/intake-pipeline.ts) turns each genuine attachment into one invoice in To Be Assigned.
2. **To Be Assigned** — needs assignee. OCR-extracted values are visually marked ([ocr-value.tsx](src/components/app/ocr-value.tsx)).
3. **To Be Coded** — coder applies GL/cost-center/tax-code lines via [/requests/[id]/coding](src/app/(site)/(app)/requests/%5Bid%5D/coding/). The GL dropdown is filtered by the coder's department (§6.14).
4. **Approval chain** — Department → Conditional → AP → Treasurer, configurable in [/settings/approval-rules](src/app/(site)/(app)/settings/approval-rules/).
5. **Ready for Processing → Processed → Completed** — batched + archived.
6. **Audit** — transitions record to AuditEvents via `recordAudit()` ([stage-engine.ts](src/backend/lib/stage-engine.ts)). Surfaced in the invoice's Log tab.

At every **forward** transition from To Be Coded onward, the coding-completeness gate runs — see §6.6. Reject and Cancel are never gated.

## 5. Architecture conventions

### 5.1. Server/client split

- **Server components** (default): pages, layouts, route segments. Fetch via `getPayload()` + `unstable_cache`-wrapped helpers in [queries.ts](src/backend/lib/queries.ts).
- **`'use client'`** for anything with state, hooks or interactivity, marked at the component boundary.
- **Server actions** (`'use server'`): mutations, in [src/backend/actions/](src/backend/actions/). **A `'use server'` file may only export async functions** — this is not a style preference, it is a hard runtime constraint. See §6.1.

### 5.2. All Requests is server-driven (changed last session)

The old design pulled every non-completed invoice with `pagination: false, limit: 0` and filtered the array in the browser. That is gone. `fetchInvoicesForTabs` and `listInvoices` no longer exist (`grep` → 0 hits each).

```
URL  ?tab= &cols= &order= &filters= &sort= &view= &page= &q= &flag=
  │
  ▼  read by the server component
requests/page.tsx
  │   compileInvoiceFilters(spec.filters, columns)  ─┐
  │   buildInvoiceSort(spec.sort, columns)          ─┤  invoice-filters.ts
  ▼                                                  │
fetchRequestsPage({ stage, search, flags,            │
                    columnClauses, sort, page })  ───┘  queries.ts
  │   → one page of rows (25) + counts for every stage tab
  ▼
RequestsScreen (client) renders; publishes counts to use-effective-counts
```

Three consequences worth holding on to:

- **The arrangement lives in the URL, not a store.** That makes the screen shareable, refresh-proof, and lets [/api/export/invoices](src/app/(site)/api/export/invoices/route.ts) answer the *same* question with the *same* compiler. There is no second code path that can drift.
- **Tab badges and the table count the same population** — `getStageCounts` receives the identical clause array.
- **Filters combine AND across columns, OR within a column**, and run against the full result set in Postgres, never against the loaded page.

Column eligibility = the built-in registry (`BUILTIN_INVOICE_COLUMNS`) ∪ every header field with `showAsColumn` on. Custom fields live in a jsonb column, so they get a *contains* box rather than a range — the Drizzle adapter's jsonb operator map has no `greater_than_equal`, and emitting one produces broken SQL.

### 5.3. Caching layers

```
┌─────────────────────────────────────────────────────┐
│  Browser tab                                        │
│  TanStack Query cache        staleTime: Infinity    │
│  - queueCounts (stages + counts + alerts)           │
│  - lookups (gl/tax/cc/projects/funds/vendors)       │
│  - invoice(id), codable-gl-accounts, reason lists   │
└─────────────────────────────────────────────────────┘
                │ server action call
                ▼
┌─────────────────────────────────────────────────────┐
│  Next.js server                                     │
│  unstable_cache               revalidate: 30s       │
│  tags: 'invoices', 'stages', 'fields'               │
│                │ getPayload                         │
│                ▼                                    │
│  Payload SDK → Postgres (Neon)                      │
└─────────────────────────────────────────────────────┘
```

**Invalidation contract**:
- Invoice mutation → `revalidateTag('invoices')`.
- Stage edit → `updateTag('stages')` in [settings-actions.ts](src/backend/actions/settings-actions.ts). Next.js 16's `updateTag` is the read-your-own-writes API for server actions; `revalidateTag` now takes a 2nd `profile` argument.
- Client mutations call `qc.invalidateQueries` OR `qc.setQueryData`.

**Gotcha inherited from `staleTime: Infinity`**: a query seeded from SSR never refetches. That is why [coding-row.tsx](src/components/app/coding-screen/coding-row.tsx) reads the *filtered* GL list on its own query key (`['codable-gl-accounts']`) instead of the shared `lookups` query — the unfiltered SSR-seeded list would otherwise have won forever.

### 5.4. Optimistic update pattern (settings tables)

Applied in [workflow-table.tsx](src/components/app/settings/workflow-table.tsx), [simple-crud.tsx](src/components/app/settings/simple-crud.tsx), [fields/index.tsx](src/components/app/settings/fields/index.tsx) and the newer settings forms:

```
1. Click → setLocalState(...) immediately
2. If state affects sidebar/lookups → qc.setQueryData(...) immediately
3. startTransition(async () => {
     try {
       const result = await upsertServerAction(...)
       // for add: swap tmp-id with result.id
       toast.success('...', { id: STABLE_TOAST_ID, duration: 1500 })
     } catch (err) {
       setLocalState(previous)            // rollback
       qc.setQueryData(prev cache)        // rollback cache mirror
       console.error('[module] ...', { id, patch, err })
       toast.error('Could not save — change rolled back', { id: STABLE_TOAST_ID })
     }
   })
4. NO router.refresh() — it was the source of 300-500ms lag.
```

**Why a deduped toast id**: rapid toggling of ten switches produces ONE evolving "Saved" pill, not a queue of ten stale messages.

### 5.5. Configuration falls back to documented defaults

**Every new configuration table was empty immediately after the schema push.** The app was expected to work anyway, so the convention throughout is: read the row, and if it is missing or partial, fall back to an exported default constant.

- `DEFAULT_CODING_RULES` ([coding-completeness.ts](src/backend/lib/coding-completeness.ts)) — a fresh database still enforces the specified sum-match rule unseeded.
- `DEFAULT_EMAIL_WRAPPER` ([email-render.ts](src/backend/lib/email-render.ts)) — previews a complete email with no `email-settings` row.
- `DEFAULT_DUPLICATE_RULE`, `DEFAULT_SENDER_POLICY`, `DEFAULT_FIELD_MAPPING`, `DEFAULT_CONFIDENCE_THRESHOLD`, `DEFAULT_ATTACHMENT_POLICY`, `DEFAULT_AMOUNT_TOLERANCE` (the `intake-*` modules).
- GL restrictions are the deliberate exception in one direction: **no format configured ⇒ restrictions off** (a fresh install must not block all coding), but **an unmapped sub-department ⇒ catch-all department**, never "open to everyone".

Reads log and degrade rather than throwing — e.g. `[coding-rules] read failed, falling back to defaults`.

**Seeds** live in [src/backend/seed/](src/backend/seed/), in two entry points:
- `seedAll()` ([seed/index.ts](src/backend/seed/index.ts)) — clears and rebuilds everything. `POST /api/seed`.
- `seedConfiguration()` ([seed/configuration.ts](src/backend/seed/configuration.ts)) — **additive**: fills empty configuration tables, skips any that already have a row, clears nothing. `POST /api/seed/configuration`. This is the one to use on an environment holding invoices somebody needs to keep.

## 6. Critical gotchas — DO NOT REPEAT

### 6.1. A `'use server'` file may only export async functions

**This took the entire app down while `tsc` reported 0 errors and every test passed.**

Next.js compiles a module-level `'use server'` file into a set of RPC endpoints. Every export must be an async function. Exporting a `const`, `let`, `var`, `enum` or `class` from one is a **build-time error that type-checking and unit tests cannot see**, because it is a framework constraint, not a type constraint. `export type` is fine — types erase at compile time.

**The check that catches it** — run it after touching anything under [src/backend/actions/](src/backend/actions/):

```sh
for f in $(grep -rln "^'use server'" src/ --include=*.ts --include=*.tsx); do
  grep -Hn "^export \(const\|let\|var\|enum\|class\) " "$f"
done
# any output at all = the app will not build
```

As of this session: **20 files carry the directive, zero violations.** Two files match the string `'use server'` only inside comments ([invoice-filters.ts](src/backend/lib/invoice-filters.ts), [GLAccounts/index.ts](src/backend/collections/GLAccounts/index.ts)) — they are not directive files and their `export const`s are legal. A naive grep flags them; do not "fix" them.

**Where a constant belongs instead**: a plain module alongside the action. That is exactly why [gl-department-routing.ts](src/backend/lib/gl-department-routing.ts) and [coding-completeness.ts](src/backend/lib/coding-completeness.ts) are `lib/` modules rather than living inside their action files.

**And the rule this bought us**: `tsc` + `eslint` + `bun test` green means nothing about whether the app runs. **Curl the routes before claiming anything works** (§8.5).

### 6.2. Payload's dev schema push turns interactive on a destructive change

The dev server pushes schema with Drizzle. Verified in the installed package, [node_modules/@payloadcms/drizzle/dist/utilities/pushDevSchema.js](node_modules/@payloadcms/drizzle/dist/utilities/pushDevSchema.js) lines 39-59: when `pushSchema` returns any warnings — which dropping a table or a column always does — it calls `prompts({ type: 'confirm', initial: false, … })` and waits on stdin, with `onCancel: () => process.exit(0)`.

**In a detached dev server there is no stdin, so it hangs forever.** Nothing in the terminal says why. `initial: false` also means that if it somehow does resolve, the default answer is "no" and the process exits silently.

**Therefore: keep schema changes additive.** Adding fields and collections is safe. Removing them is a deliberate, foregrounded operation done with the dev server stopped and a real terminal attached.

**Three fields are retained hidden for exactly this reason.** Each is dead code kept only to hold its Postgres column in place, each is `admin: { hidden: true }` so it cannot look like a working setting, and each carries a comment saying so:

| Field | File | Why it is dead |
|---|---|---|
| `Stages.tone` | [Stages/index.ts](src/backend/collections/Stages/index.ts) | Status pills are now a brand-derived ramp by stage position (§6.10). A stored per-stage hue governs nothing. |
| `Fields.exportable` | [Fields/index.ts](src/backend/collections/Fields/index.ts) | The per-field CSV export toggle is retired — CSV export follows the on-screen view (§6.12). Nothing reads it and no screen shows it. |
| `GLAccounts.segments` | [GLAccounts/index.ts](src/backend/collections/GLAccounts/index.ts) | A GL code is split on demand by the configured mask. The array was never populated by any hook. Dropping it would drop the `gl_accounts_segments` table. |

Removing all three (plus the retired `CodingRestrictions` tables) is a single deliberate migration for a future session. Delete the field and the column together, with a real terminal.

### 6.3. React Compiler + TanStack Table memoization

**Symptom**: Click a Switch / Checkbox in a TanStack-table-using component → state changes but the visual indicator doesn't update.

**Cause**: `reactCompiler: true` auto-memoizes function components. A component receiving `table`/`column`/`row` as a prop has STABLE references, so the compiler skips re-render — but `row.getIsSelected()`, `column.getIsSorted()`, `table.getState()` are method-call reads whose results ARE reactive. The compiler doesn't track them as deps.

**Fix**: `'use no memo'` as the first statement of the function body.

**Currently applied in**: [column-header.tsx](src/components/ui/data-table/column-header.tsx), [view-options.tsx](src/components/ui/data-table/view-options.tsx), [invoice-table/toolbar.tsx](src/components/app/invoice-table/toolbar.tsx).

**Additionally**: DataTable's row rendering is INLINE. A prior extracted `<RowGroup>` was the source of the original row-checkbox bug — extracting created a memoization boundary. **DO NOT** extract row rendering unless you also add `'use no memo'`.

**Rule for new code**: if your component takes `table: Table<T>`, `column: Column<T>` or `row: Row<T>` AND reads any `.getIs*()` / `.getCan*()` / `.getState()` method, add `'use no memo'`.

### 6.4. shadcn primitives shipped wrong Tailwind selectors

**Symptom**: the `checked` prop is true but the visual state stays unchecked.

**Cause**: shadcn-generated components used `data-checked:bg-primary`, which Tailwind v4 reads as `[data-checked]`. But `radix-ui` Checkbox/Switch/RadioGroup set `data-state="checked"`, so the rules never match.

**Fixed in**: [checkbox.tsx](src/components/ui/checkbox.tsx), [switch.tsx](src/components/ui/switch.tsx), [radio-group.tsx](src/components/ui/radio-group.tsx), [field.tsx](src/components/ui/field.tsx).

**Still potentially affected (not user-reported)**: [tabs.tsx](src/components/ui/tabs.tsx) uses `data-active:`/`data-horizontal:`.

**Rule**: after regenerating any shadcn component, grep the new file for `data-checked:`, `data-unchecked:`, `data-active:`, `has-data-checked:`. If the primitive comes from `radix-ui`, replace with `data-[state=X]:`.

### 6.5. Invoice header amounts are vendor facts, NOT derived from coding lines

A `recomputeInvoiceTotals()` helper used to overwrite `subtotal` / `totalTax` / `grandTotal` from the sum of the coding lines on **every** line save and delete. **It is gone** — the only remaining occurrence repo-wide is a tombstone comment at [_helpers.ts:15](src/backend/actions/invoice/_helpers.ts).

Two things were wrong with it:

1. **It made the sum-match rule vacuous.** After any line save the coded sum always equalled the header, so the reconciliation check could never fire — the exact rule the client asked to be enforced.
2. **It would have destroyed OCR-extracted amounts.** Email intake reads the three amounts off the scan. A line save would have silently overwritten what the vendor's own invoice says.

The three amounts are now header facts, typed on the New Invoice form or extracted by OCR. They are correctable on the Header tab through [`updateInvoiceAmounts`](src/backend/actions/invoice/amounts.ts), which validates (rejects non-finite and negative), audits `previous`/`next`, and moves the `flags.amountMismatch` flag with the correction. That correction path is **mandatory, not optional**: the gate below blocks a coder who has no other way to fix the number they are measured against.

**Do not reintroduce derivation.** If you find yourself writing header totals from line totals, you are recreating the bug.

### 6.6. The coding-completeness gate keys on the STAGE, not on line count

The gate lives in [`approveInvoice`](src/backend/actions/invoice/transitions.ts) and is server-authoritative — the coding screen and the Approve button only mirror it.

The guard is `isAtOrPastCoding(currentSysId)` ([stage-ids.ts](src/backend/lib/stage-ids.ts)), **deliberately not** "does this invoice have lines". Keying it on line count left a real hole: deleting every line at a later stage took the count to zero, which read as "nothing to check", and a wholly uncoded invoice approved straight through. An invoice that has reached the coding stage owes a complete coding from then on, whatever its table currently holds.

"Fully coded" is three conditions, per the spec: at least one line, every line has a GL account, and the lines reconcile against the configured target (default Amount Before Taxes). **Tax Code is deliberately excluded** — coders are trained not to enter it.

Behaviour is read from Settings → Coding Table, never hardcoded: `block` throws the configured message, `warn` throws unless `acknowledgedWarning` is set and audits the acknowledgement, `disabled` skips. **Reject and Cancel bypass all of it** — an invoice that cannot be coded correctly still has to be able to go backwards.

**Known limits, stated honestly**: `acknowledgedWarning` is a client-supplied boolean, so `warn` is advisory by construction — only `block` is unbypassable. Multi-department invoices are exempt until the final department submits (`enforced = outstandingDepartments.length <= 1`), otherwise no single coder could ever make the lines reconcile and the invoice would deadlock.

### 6.7. Coding tab navigates to a separate page

The "Coding" tab inside an invoice view is **navigational**, not a content-swap. Clicking it routes to `/requests/[id]/coding` (preview-left, table-right). Other tabs (Header/Files/Notes/Log) stay client-side state on `/requests/[id]`. Implemented in [invoice-view/index.tsx](src/components/app/invoice-view/index.tsx).

In the coding screen the other tabs navigate back to `/requests/[id]?tab=<name>`; the invoice page redirects `?tab=coding` server-side.

**DO NOT** re-add a read-only coding summary. If users say "the Coding tab is empty" — that is wrong intuition; it should navigate.

### 6.8. PDF preview: two separate fixes, both still needed

**(a) Storage.** Every PDF failed with pdf.js's "Failed to load PDF document", and downloads came back empty. The viewer was only the messenger: Payload's `/api/documents/file/<name>` handler HEADs UploadThing's signed URL and trusts `content-length` to build the response. UploadThing does not send that header, so the handler computed a size of 0 and emitted `Content-Length: 0`. Range requests fared worse — a size of 0 makes every range unsatisfiable, so Chrome's viewer got a 416.

Fixed by `documents: { disablePayloadAccessControl: true }` in [payload.config.ts](src/payload.config.ts), which makes the plugin's `afterRead` hook rewrite `url` to the CDN address on every read — repairing rows written before the fix with no data migration.

**Trade-off, written down because it matters at auth time**: file bytes now sit outside Payload access control. That was already effectively true (`acl: 'public-read'`), but the correct shape once auth lands is a private ACL plus a signed-URL redirect route.

**(b) Iframe remount.** Chrome's PDF viewer doesn't reliably swap when only `src` changes. [pdf-preview.tsx](src/components/app/pdf-preview.tsx) uses `<iframe key={`${doc.id}:${doc.url}`}>` to force a remount on doc change.

### 6.9. Documents collection needs explicit `access.read`

Payload's default access policy denies anonymous reads, and the preview iframe is anonymous in the demo. [Documents/index.ts](src/backend/collections/Documents/index.ts) sets `access: { read: () => true }`.

**When auth lands** (§7.1): replace with `access: { read: ({ req: { user } }) => Boolean(user) }`, together with the storage trade-off in §6.8(a).

### 6.10. Dynamic stage labels, and status pill colour

Hardcoded `STAGE_LABELS` in [stage-ids.ts](src/backend/lib/stage-ids.ts) is only a **fallback**. Real labels come from the database through [use-stage-labels.ts](src/hooks/use-stage-labels.ts), which reads the `stages` array off the `queueCounts` TanStack cache (refreshed by `getStageDefinitions()`). Used by `StageBadge`, `WorkflowStepper`, `RejectMenu`, `RequestsTabs`, `SidebarNav` — all re-render when an admin renames a stage.

**`STAGE_TONE` no longer exists** (`grep` → 0 hits). Status pills in [stage-badge.tsx](src/components/app/stage-badge.tsx) are a **single-hue ramp derived from the brand colour by stage position**: neutral grey for not-started, deepening `color-mix` tints of `--primary` through the working stages, solid brand for the two late stages, green for done. Re-skinning to another municipality's brand re-tints the whole ramp with no further work. Every combination was measured against WCAG 2.2 AA — the ramp stops at 36% because 44% falls to 4.21:1 and fails.

The previous implementation hardcoded unrelated Tailwind hues (blue, violet, amber) that could never follow the brand. Do not reintroduce a per-stage hue.

### 6.11. Bun/tsx CANNOT load Payload directly

`bun script.mjs` or `bunx tsx script.ts` doing `import { getPayload } from 'payload'` crashes with `ReferenceError: Cannot access 'DecoratorNode' before initialization` (Lexical circular CJS/ESM dep).

**Workarounds for one-off DB tasks**:
- Add a temporary Next.js API route → curl it locally → remove. This is the preferred path, and it is why `/api/seed` and `/api/seed/configuration` exist as routes rather than scripts.
- Direct SQL via `import { SQL } from 'bun'` + `DATABASE_URL_UNPOOLED`. **Caveat**: bypasses Payload hooks, cache invalidation tags and audit logging.

**Lesson learned**: a previous session bypassed the `updateStage` server action and wrote raw SQL to restore a stage label. That skipped `updateTag('stages')`, so the sidebar didn't update until a manual refresh. Use the server action path.

### 6.12. CSV export follows the on-screen view — there is no fixed-shape export

There is exactly one export mechanism. [/api/export/invoices](src/app/(site)/api/export/invoices/route.ts) reuses the same URL parameters and the same filter compiler as the screen, so it exports the current filters, the current columns, the current column order and the current sort — for every row matching the filter, not just the loaded page (capped at `EXPORT_ROW_CAP = 5000`).

The dead "Export" button on All Requests is removed. "Export CSV" is the working one.

**The per-field CSV export toggle is retired.** It existed only to define the fixed ERP export's column set; that export is dropped, so the toggle governed nothing, and a setting that appears to control exports but does not is worse than none. The `Fields.exportable` column survives as a hidden dead field — see §6.2 for why it was not dropped.

### 6.13. The brand palette deliberately diverges from its design source in three places

The palette is ported from the revamped City Connections reference build. **Three values intentionally do not match the source**, because the design brief asks for the revamp specifically so the interface meets WCAG 2.2 AA and those three do not. The full reasoning, with measured contrast ratios rather than estimates, is in the comment block at the top of [globals.css](src/app/(site)/globals.css). In brief:

- `--dim #8C98A8` as body text is 2.93:1 — fails AA. Secondary text uses `--slate #56657A` (5.94:1); `#8C98A8` survives only for decorative icons.
- `--coral #FB6E4B` behind white text is 2.82:1 — fails AA. Destructive surfaces use `#C2410C` (5.18:1); coral stays an accent, never a label background.
- `--line #E5EBF3` as a form-control edge is 1.20:1 — fails 1.4.11 (needs 3:1). `--border` keeps it for decorative rules, but `--input`, which draws the boundary of every text box, is `#828EA0` (3.32:1). This is what makes "white input boxes, no monochromatic fields" legible rather than merely pale.

**If someone asks why the app doesn't match the mockup exactly, this is the answer.** Do not "correct" these three back to the source values.

### 6.14. GL coding restrictions are a range table, not a per-department rule builder

The old model (per-department rules of the form "Segment N matches value") is retired. The current model, taken from the Central Frontenac design:

- A **mask** with a label per segment (e.g. `XX-XXX-XXXX-XXXXX` → Fund, Function, Sub-department, Object). **Segments are different lengths** — any model assuming uniform width is wrong. One segment is nominated as carrying the department.
- **Ranges** of that segment map to departments, in [department-segment-map](src/backend/collections/DepartmentSegmentMap/index.ts). A department can hold several discontiguous rows, and a single value always overrides the range it sits inside. Central Frontenac's 544 sub-departments are covered by about 24 rows.
- **Unmapped values route to a configurable catch-all department** — fail-closed, never "open to everyone". Settings lists what is currently hitting the catch-all so an admin can see new sub-departments appear.

The engine is [segments.ts](src/backend/lib/segments.ts) (pure, tested); the loader and enforcement are [gl-department-routing.ts](src/backend/lib/gl-department-routing.ts). Precedence is single value → narrowest containing range → catch-all. A code that does not fit the mask resolves to the catch-all, never to "unrestricted".

### 6.15. Left-nav path matching must be exact, not a prefix

Clicking a queue in the left nav while an invoice was open did nothing — the highlight moved but the page never changed, so the navigation reported a location the user was not at.

Cause: `/requests/<id>` and `/requests/<id>/coding` were treated as "already on the list" by a prefix match, so the code set the tab store and skipped the navigation. Fixed in [requests-routes.ts](src/lib/requests-routes.ts): `isRequestsListPath` is an **exact** `=== '/requests'` comparison, and `isInvoiceDetailPath` is the prefix test.

Related: the queue now travels in the address (`?tab=`), not only in the store, because All Requests answers from the server. A bare `/requests` means "all". `requestsListHref(tab)` is the single place that builds the link.

### 6.16. SystemId badges leak technical detail to non-tech users

The workflow settings table shows badges like `to_be_coded`, `ap_review` next to each stage label. Useful for admin/dev, **not** appropriate for client demos. Same risk: ID columns in tables, `tmp-…` client-side temp IDs that may briefly flash, raw stack traces in error toasts. Still open — see §7.4.

### 8.6. Verification handoff — give the user steps, don't drive a browser

The user is the eyes and hands. When a change affects runtime behaviour, end with a short numbered list: what to click / what URL to open, what to look for, what to expect. Plain language, no jargon.

If the user explicitly asks for programmatic verification, headless Brave via CDP is available at `$env:LOCALAPPDATA\BraveSoftware\Brave-Browser\Application\brave.exe` with `--remote-debugging-port`. CDP gotchas:
- `getBoundingClientRect()` doesn't JSON.stringify — project to `{x, y, width, height}` manually.
- `inp.dispatchEvent(new Event('blur'))` does NOT trigger React's `onBlur`. Click elsewhere via `Input.dispatchMouseEvent`, or call `inp.blur()`.
- For Radix triggers: send `mouseMoved` before `mousePressed`, with `pointerType: 'mouse'`.
- CDP rejects fractional doubles for mouse coords — `Math.round(x, y)`.

Programmatic verification is opt-in by user request. Handoff is the default.

## 10. Verification Handoff (MANDATORY)

I cannot run a browser in the real world; the user can. When a change affects runtime behaviour (UI, API response, side effects), end the response with a short numbered list:

1. What to click / what URL or command to run
2. What to look for (specific visual state, console output, response field)
3. What to expect (the correct outcome)

Plain language, no jargon. The user is the eyes and hands; be honest about what you have not run yourself.

**`tsc` + `eslint` + `bun test` clean is necessary but NOT sufficient.** This is not a slogan — it is the measured behaviour of this repo:

- A `'use server'` file exporting a constant took the whole app down with 0 type errors and 305 passing tests (§6.1).
- State-driven UI bugs — checkboxes that don't toggle visually, sort arrows that don't update, an inert nav button under a moving highlight — slip past all three (§6.3, §6.15).

**Minimum bar before saying something works**: type-check, tests, AND a curl of the affected route (§8.5). Anything click-level goes to the user as numbered steps.

### Pushback when "done" is claimed without runtime verification

> "tsc/lint/tests clean and the route answers 200. Click-level behaviour not verified. Steps to check: 1) …, 2) …, 3) …"

Past failure mode: declaring "production-correct" on `tsc --noEmit` + `eslint` exit-zero. Bugs visible only at runtime surfaced in front of clients. Do not repeat.

## 14. Things previous sessions got wrong (learn from these)

- **Declared "production correct" without running the result anywhere.** Shipped regressions followed. The fix is verification handoff with numbered steps, not silent declaration of "done".
- **Trusted green checks that could not see the failure.** A `'use server'` file exporting a constant took the app down with `tsc` at 0 errors and 305 tests passing. Green type-checks and green tests are evidence about types and logic, and about nothing else. Curl the route (§8.1, §8.5).
- **Over-architected.** Extracting `<RowGroup>` from DataTable created a React Compiler memoization boundary that broke row checkbox state. Canonical patterns exist because they work.
- **Grepped narrowly.** Fixed Checkbox CSS but not Switch/Radio/Field with the same bug class, so bugs surfaced one at a time across several turns instead of being swept once.
- **Bypassed our own architecture for convenience.** Raw SQL to fix a test artifact skipped `updateTag('stages')` and left the sidebar stale. The right way was harder to set up, but not by much.
- **Made single-user assumptions that don't fit the product.** This is a municipal AP system with multiple roles. Don't bake in "trust local state forever" patterns.
- **Confused "demo" with "stub".** Demo quality means a non-technical viewer sees a polished product — no leaked tech labels, no jank. Engineer-acceptable shortcuts are exactly what reads as unfinished to the audience.
- **Derived a value that was actually an input.** `recomputeInvoiceTotals` overwrote header amounts from coding lines. It silently made the sum-match rule vacuous, and would have destroyed every OCR-extracted amount the moment intake shipped. Before deriving a field, ask where its value comes from when nobody has computed it yet.
- **Wrote a guard against the wrong question.** The coding gate first asked "does this invoice have lines" instead of "has this invoice reached the coding stage", which left a bypass reachable by deleting every line. A guard keyed on mutable state that the user controls is not a guard.
- **Let this file go stale.** Large parts of it described mechanisms that had been replaced hours earlier, and it was trusted while stale. Update it in the same session as the change.

**The single most important rule** for this codebase: **don't claim verification you didn't perform.** State exactly which checks you ran, and hand the rest to the user as numbered steps.
