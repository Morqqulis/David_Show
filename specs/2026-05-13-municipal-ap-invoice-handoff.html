Home / Dashboard

Route: #home · Sidebar: Home (top item)
app://homeOpen ↗
Capture screenshot of #home here when generating PDF.
Welcome page · 4 KPI cards · Quick Access list · Recent Activity

What this page does

Landing screen after sign-in. Gives the AP user an at-a-glance read on what they need to act on today and quick jumps into the most-used queues.

Requirements

  1. Hero header with the municipality name, app name, current date, and a one-line description of the application.
  2. A primary + New Invoice CTA card on the left of the stats row that routes to #create-invoice.
  3. Four stat cards along the top: In My Queues, Pending My Action, Alerts (red), and On-Time Rate. Counts are computed live from the user's queues, OCR/duplicate flags, and archive-failure list.
  4. Quick Access list — a card showing the queues that matter most to this user (To Be Assigned, To Be Coded, AP Review, Treasurer Review by default). Each row has a colored count pill matching the stage color, the queue name, a one-line meta detail (e.g., "5 in your dept"), and routes to that queue on click.
  5. Recent Activity timeline — last ~5 system-wide actions (close_batch, approve, reject, code, ingest). Same event format as the per-invoice Log tab. Read-only; this is awareness, not action.
  6. Layout is two-column on wide screens (Quick Access + Activity side-by-side) and stacks on narrow.
  7. No table on this page — All Requests is one click away via the sidebar or the "View all requests →" link in the Quick Access header.
Spec reference: none specifically — this is the assembled landing view of stats and shortcuts derived from queues and audit log. Stage list comes from Section 4.

Master list of every invoice across every stage · stage pill nav · row stats · expandable rows

What this page does

The master list of every invoice in the system across every stage. Doubles as the global search surface and the entry point to the inline preview/coding view.

Requirements

  1. Stage pill bar at the top: one pill per stage (All, To Be Assigned, To Be Coded, Conditional Approvals, AP Review, Ready for Processing, Processed, Treasurer Review, Completed). Each pill carries a live count. Active pill is filled blue; clicking scopes the table.
  2. Stat row showing per-stage counts (subset of the most useful ones).
  3. Toolbar: global free-text search input, vendor filter, department filter, date range pickers, columns selector button.
  4. Search spans invoice number, vendor, batch number, date range, amount, and free text in comments and notes. (Section 8.7)
  5. Configurable columns driven by Settings → Fields. Any field with "Show as column on All Requests" enabled appears as a column. No saved views in v1 — per-user show/hide only. (Section 8.8)
  6. Inline row expansion: each row has an expand chevron at the left. Expanding shows a two-pane card under the row with the invoice preview (left) and the coding table (right) — both editable inline if the user has permission at the current stage. (Section 8.8a)
  7. Each row also has an Open ↗ button that navigates to the dedicated Invoice screen (#invoice) for full split-view + activity tabs.
  8. Row flags: rows marked OCR Failed, Vendor Setup Required, or Low OCR Confidence get an amber row tint and a small inline pill in the Vendor cell.
  9. Bulk actions via the checkbox column: assign, batch # apply, approve, reassign, export. (Section 8.6)
  10. Status pill colors are consistent with the stage colors used on Home and the queue pages.
  11. Pagination: pager at the bottom with total record count.
Spec references: §8.7 Global Search · §8.8 All Requests Screen · §8.8a Inline row expansion · §8.6 Bulk Actions · §5a Field-driven columns.

Route: #to-be-assigned · Sidebar: Queues (default landing)
app://to-be-assignedOpen ↗
Capture screenshot of #to-be-assigned here when generating PDF.
Stage 1 of 8 · intake landing zone · OCR/vendor flags surfaced

What this page does

Initial queue for every newly created invoice (email or manual). AP staff triage flagged items, assign to coders or departments (single or bulk), and set the Vendor Setup Required flag where needed.

Requirements

  1. Hero with stage label and a one-line description; Bulk Assign and ↓ Export in the hero actions.
  2. Stage pill bar at the top (same as All Requests) with the active pill highlighted.
  3. Banner summarizing flagged requests count with a one-line breakdown (e.g., "1 OCR failed, 1 unmatched vendor, 1 low-confidence vendor match").
  4. Toolbar: search, flag filter (All flags / OCR Failed / Vendor Setup Required / Low Confidence), sort selector (Oldest first / Newest first / Amount).
  5. Table columns: Received, Invoice #, Vendor, Flags, Amount, Source, per-row Assign action.
  6. Flag pills are red for hard errors (OCR Failed, Vendor Setup Req.), amber for warnings (Low Confidence with extracted %).
  7. Source column shows where the request originated (Email or Manual + creator).
  8. Vendor Setup Required blocks advancement: AP can either select an existing vendor from the synced list or wait for the new vendor to be added in the ERP and synced. (Section 6.3)
  9. Bulk assign is configurable per-stage (per Section 4a) and is enabled here by default.
Spec references: §6.3 To Be Assigned · §6.1 OCR/intake edge cases · §4a per-stage Bulk Assign config.

Conditional Approvals

Route: #conditional-approvals
app://conditional-approvalsOpen ↗
Capture screenshot of #conditional-approvals here when generating PDF.
Stage 3 of 8 · only invoices that triggered at least one rule appear; auto-skipped otherwise

What this page does

Stage between coding and AP review where invoices that match one or more approval rules are routed to additional approvers (CAO sign-off, Library Director on Library invoices, etc.). Invoices that don't trigger any rule auto-skip this stage entirely.

Requirements

  1. Stage pill bar with Conditional Approvals active.
  2. Table columns: Invoice #, Vendor, Department, Triggered Rule(s) (one or more pills naming the matched rules), Amount, Co-approvers, Routed (relative time), per-row Reject + Approve actions.
  3. Multiple matching rules add together (deduplicated) — every approver from every matched rule is required. (Section 6.5)
  4. Required approvers per rule default to Parallel (both notified at once, both must approve). Configurable per rule.
  5. Reject path: same pattern as elsewhere — reason required, rejecter chooses destination stage. (Section 8.4)
  6. Approval rules themselves are configured in Settings → Approval Rules (page 21 in this handoff).
Spec references: §6.5 Conditional Approvals · §8.4 Reject & Reassign pattern.

Stage 4 of 8 · final finance gate before processing

What this page does

Final finance gate before invoices are released for batching and ERP import. AP can edit any field, reject back to specific upstream reviewers (granular, not blanket), or approve to advance.

  2. Hero action: Bulk Approve.

  6. Approval here advances the invoice to Ready for Processing.

Ready for Processing

Route: #ready-for-processing
app://ready-for-processingOpen ↗
Capture screenshot of #ready-for-processing here when generating PDF.
Stage 5 of 8 · batch numbers applied here · CSV export to ERP

What this page does

AP-approved invoices waiting to be batched. The single place where batch numbers are applied (this is the only stage with Batch Assign enabled). AP exports a CSV against any active filter for import into the financial system.

Requirements

  1. Hero actions: Apply Batch # and ↓ Export CSV.
  2. Stage pill bar with this stage active.
  3. Selection banner: when invoices are selected, show count + sum total (e.g., "Selected: 3 invoices, $42,896.89").
  4. Apply Batch # picker: free-form text input. Warn (not block) if the entered batch number has been used before; AP must confirm. (Section 6.7)
  5. Applying a batch number to one or more invoices advances them to the Processed stage. (Section 4 lifecycle)
  6. Export CSV uses the configured field list from Settings → Export Format. Active filter scopes the export. (Section 6.7)
  7. Re-export of the same filter is safe — no status change is triggered by the export action; the export itself is captured in audit. (Section 6.7, §8.2)
  8. Table columns: Invoice #, Vendor, Department, Approved By, Amount, Approved time. Checkbox column for selection.
  9. Batch Assign per-stage config is locked ON for this stage and unavailable elsewhere in v1. (Section 4a)
Spec references: §6.7 Ready for Processing · §4a per-stage Batch Assign · §8.2 Audit Log entries for batch_applied / export.

Treasurer Review

Route: #treasurer-review
app://treasurer-reviewOpen ↗
Capture screenshot of #treasurer-review here when generating PDF.
Stage 7 of 8 · grouped by batch · per-row + bulk Verify · Approve / Close Batch

What this page does

Treasurer's spot-check stage. Invoices are grouped by batch here, not flat. The treasurer opens individual invoices, marks them Verified (single or bulk), and when satisfied, closes the batch — releasing all remaining invoices to Completed.

Requirements

  1. Page is grouped: each batch is its own card with header (batch # mono, status pill, count + total, per-row actions).
  2. Per-batch actions: Reject Invoice, Bulk Verify, Approve / Close Batch.
  3. Per-row actions: Verify / Unverify toggle, Open (routes to Invoice screen).
  4. Verify is a marker, not a stage transition — not all invoices in a batch need to be verified; it's a spot-check. (Section 6.9)
  5. Reject: rejecter picks destination stage (default AP Review). The rejected invoice's batch number is wiped; AP is notified; other invoices in the batch are unaffected. (Section 6.9)
  6. Approve / Close Batch: moves all remaining invoices in the batch to Completed (which triggers SharePoint archive).
  7. Verify Flag is configurable per-stage (Section 4a) and shipped ON here; can be enabled at other stages too if a client wants additional checkpoints.
  8. Bulk Verify = checkbox column + top-level button on the batch table.
Spec references: §6.9 Treasurer Review · §4a Verify Flag per-stage · §8.6 Bulk Actions.

Completed

Route: #completed
app://completedOpen ↗
Capture screenshot of #completed here when generating PDF.
Stage 8 of 8 (terminal) · auto-archived to SharePoint · retry status visible

What this page does

Terminal queue. Invoices that have cleared treasurer review. Each completed invoice triggers the SharePoint archive automatically; the Archive column shows the result of that operation.

Requirements

  1. Hero action: ↓ Export.
  2. Stage pill bar with Completed active.
  3. Toolbar: search, period selector (Last 30 days / This fiscal year / All time).
  4. Table columns: Invoice #, Vendor, Batch # (mono), Department, Amount, Completed time, Archive status pill, Open action.
  5. Archive pill: green "Archived" on success, amber "Retry N/5" while retries are running, red Failed once retries are exhausted. (Section 6.10)
  6. Retry runs in background with exponential backoff (1m, 5m, 30m, 1h, 6h). After 5 failed attempts, the invoice surfaces in Alerts.
  7. Document Set name follows the configurable token pattern (e.g., {Vendor}_{InvoiceNumber}_{InvoiceDate}) and inherits the SharePoint library's retention label.
Spec references: §6.10 Completed · §8.1 Document Management (archive failure handling).

Invoice Screen (deep view)

Route: #invoice · Reached from row click on All Requests, Open ↗ buttons, or Treasurer Review row Open
app://invoice/INV-2026-0345Open ↗
Capture screenshot of #invoice here when generating PDF.
Two-col layout · invoice preview + right-pane tabs · workflow stepper · collapsible preview

What this page does

The full deep-view of a single invoice — used at every stage by the role acting on it. Hosts the invoice document, all header metadata, the coding table, attached files, the comment thread, and the per-invoice audit log, all in one screen.

Requirements

  1. Hero header with stage category pill, invoice ID + vendor as the title, a one-line context (e.g., "Posted in batch X · Verified by Y · $1,130.00"), and three primary actions in the top-right: ↑ Reassign, Reject, Approve.
  2. Full-width 8-step workflow stepper below the hero. Each stage is a numbered circle; completed stages are filled blue with a checkmark; current stage is filled blue with a soft ring; future stages are gray-outlined. Stepper labels are configurable per Section 4a status labels.
  3. Two-column split: invoice preview (left) + right-pane tabs.
  4. Invoice preview pane is collapsible — toggle in the pane header collapses to a ~44px vertical strip showing only the doc name. Click again to expand.
  5. Right-pane tabs (single row): Header (default) · Coding · Files · Notes · Log.
  6. Header tab: all header fields rendered in their configured Sections (Section 5a). Each field uses its configured Width (Full / 1/2 / 1/3 / 1/4). Editable per Fields Editable By role at the current stage. Section pills are numbered card-num badges (e.g., "1 · DETAILS").
  7. Coding tab: the invoice's coded lines inline using the same coding table component as the dedicated Coding screen. Same validation row at the bottom. Add Line button at top.
  8. Files tab: list of attached documents with name, size, uploader, and timestamp. Clicking a document swaps the left-pane preview to that document and updates the preview header label. (Section 8.1)
  9. Notes tab: per-invoice comment thread; date/time stamped; supports @mentions (in-app notification fired). Composer at the bottom with a textarea + Post button.
  10. Log tab: per-invoice audit timeline. Action-based events only (no field-edit logging). Each event line is "When · Who" + bold action + context. There is no global Audit Log screen — audit is always per-invoice. (Section 8.2)
  11. If the invoice is marked Confidential, a small lock indicator appears on the title row; the entire screen returns 404 for users without the Confidential role flag. (Section 5b)
Spec references: §8.1 Invoice screen layout · §5a Field-driven sections · §5b Confidential filtering · §8.2 Audit Log · §8.4 Reject & Reassign actions.

Coding Screen

Route: #coding · Reached from To Be Coded row click and the Open Coding ↗ links
app://coding/INV-2026-0339Open ↗
Capture screenshot of #coding here when generating PDF.
Same shell as Invoice screen with Coding as the default tab and a wider right pane (1fr / 1.4fr)

What this page does

Same shell as the Invoice screen, but with Coding as the default tab and a wider right pane. Designed for coders who land here from the To Be Coded queue and primarily need to fill out the coding table while glancing at the invoice.

Requirements

  1. Two-column split with grid 1fr / 1.4fr (invoice preview narrower than coding pane).
  2. Right-pane tabs: Coding (default) · Header · Files · Notes · Log — same set as Invoice screen, different default.
  3. Coding table with one row per coded line. Columns: GL Account, Cost Center, Project (and any other configured Coding Line fields), Amount, Tax Code, computed Tax / Recoverable / Non-Rec. (visibility configurable). Footer row totals each numeric column. (Section 7.1)
  4. Validation row below the table: Σ Lines = Subtotal · Σ Tax = Header Tax · Σ Total = Grand Total. Green when matched; red with the variance when not.
  5. Sum-match enforcement: per Settings → Coding Table, the sum check matches against Subtotal (default), Grand Total, or is Disabled; on mismatch the action is Block (default) or Warn. (Section 7.4)
  6. Approval status chips below the table: avatar + name + Pending/Approved pill for each assignee. Multi-recipient stages require all to approve.
  7. GL filtering by department coding restrictions: the GL dropdown for a coder is filtered live to GLs matching their department's segment-based rule(s). Roles with the Bypass Coding Restrictions flag see all GLs. (Section 7.5)
  8. Add Line button in the Coding tab header.
  9. Same stepper, same invoice preview (collapsible), same hero actions as Invoice screen.
Spec references: §7.1 Coding Table · §7.2 Tax Calculation · §7.4 Validation (sum-match) · §7.5 Coding Restrictions · §8.1 layout.

Manual entry path · no OCR runs against attached files · same lifecycle from To Be Assigned

What this page does

For invoices that don't arrive through the AP mailbox (vendor walk-in, special handling, etc.). All header data is keyed in manually; OCR is intentionally not run against any attached files in this path. After submission the invoice enters the lifecycle at To Be Assigned.

Requirements

  6. Vendor field is a Lookup driven by the synced ERP vendor list.
  7. Attachments dropzone: PDF, Word, JPG, PNG, TIFF; up to 10 per request, 50 MB per file. (Section 8.1)
  8. "Need a different field?" link routes to Settings → Fields — admins manage field schema there, not from this form.
  9. On Submit, the request lands in To Be Assigned with no OCR run.
  10. The right-side activity card (Status / Files / Notes / Log) is visible but Files/Notes/Log are empty until after submission.

Email — Templates

Route: #email + Templates tab · Sidebar: Email
app://email#templatesOpen ↗
Capture screenshot of #email Templates tab here when generating PDF.
Two-pane: template list + editor · token chips · WYSIWYG body editor

What this page does

Library of named, reusable HTML templates. Each template has a name, subject, and body; tokens are interpolated at send time. Templates are bound to events on the Triggers tab.

Requirements

  1. Two-pane layout: template list (left rail), editor (right card).
  2. Left rail: + New Template button at top, then list of templates with name + one-line description; selected template highlighted.
  3. Editor: name field, subject field, body (WYSIWYG), token-chip palette above the inputs.
  4. Editor toolbar: Send test (sends to the current admin), Delete, Save.
  5. Token chips insert at the cursor position in subject or body when clicked. Token list (Section 8.3): {{InvoiceNumber}}, {{Vendor}}, {{InvoiceDate}}, {{DueDate}}, {{Amount}}, {{Status}}, {{Stage}}, {{BatchNumber}}, {{Assignee}}, {{Approver}}, {{Rejecter}}, {{RejectReason}}, {{InvoiceURL}}, {{Department}}, {{Municipality}}, {{AppName}}.
  6. Body is automatically wrapped by the global header and footer (set on the Settings tab) at send time.
  7. WYSIWYG editor must support: bold/italic/underline/strikethrough, font + size selectors, text + highlight color, alignment, lists, indent, link, image, clear formatting.
  8. Tokens that resolve to nothing at send time render as empty (no error).
Spec references: §8.3 Notifications & Email — Templates section.

Email — Triggers

Route: #email + Triggers tab
app://email#triggersOpen ↗
Capture screenshot of #email Triggers tab here when generating PDF.
Event × Stage → Template + Recipients + CC · four recipient types

What this page does

Decides which template fires when. Each row maps a system event firing at a specific stage to a single template plus a list of recipients (and optional CC list).

Requirements

  1. Table columns: Event, Stage, Template, Recipients, CC, Status (Active / Disabled), Edit action.
  2. Events in v1: Submission, Approval, Rejection, Reassignment, Conditional Routing, Treasurer Routing, Batch Applied, Archive Failed.
  3. Stage can be a specific stage or "(any)" — the same event can fire different templates depending on which stage it happens at (e.g., Approval @ To Be Coded vs. Approval @ AP Review).
  4. Recipients are picked from a four-tab picker: Dynamic role, Group, Person, Email. Each chip shows its type via color.
  5. Dynamic role recipients resolve at send time (e.g., "the Approver", "the Rejecter", "the AP Supervisor for the dept"); if a slot resolves to nobody, that slot is silently skipped — others on the trigger still get the email.
  6. Triggers can be enabled or disabled without deleting them.
  7. + Add Trigger button creates a new row.
  8. The Recipient picker preview at the bottom of the page is illustrative, showing the four chip types side-by-side.
Spec references: §8.3 Notifications & Email — Triggers + Recipients sections.

Settings — Fields

Route: #settings + Fields tab
app://settings#fieldsOpen ↗
Capture screenshot of #settings Fields tab here when generating PDF.
Header Sections manager + full Fields config matrix + Add Field picker preview

What this page does

The schema editor. Defines every header field, every coded-line field, and the named header sections that group header fields. Drives the New Request form, the Invoice screen Header tab, the coding table, the All Requests columns, the CSV export, and approval rule conditions.

Requirements

  1. Header Sections manager at the top: list of named sections in order (Details, Amounts, Workflow, Custom by default), each row is the section name (editable) plus field count plus reorder/delete actions. + Add Section button. Removing a section reassigns its fields to the first remaining section.
  2. Fields config matrix. Columns: Field Label, Scope (Header / Coding Line pill), Section (dropdown for Header fields, n/a for Coding Line), Type, Width (Header only), Options, Mandatory at stage (clickable pills per stage), All Reqs col toggle, Export toggle, Edit / Delete actions.
  3. System fields are locked from removal (lock icon, gray row tint) but every other property is still editable. Custom fields can be deleted.
  4. Mandatory pill toggles: click any pill to toggle that stage as required for this field. Required-at-one carries forward — once a field is satisfied, it can't become unfilled later.
  5. Options column behavior:
